# ES-40 + ESX-8GT / ESX-8CV setup

Studio supports the ES-40's encoded S/PDIF transport, with one ESX-8GT or ESX-8CV
per configured unit. This is separate from the direct DC audio used by an ES-3.
Choose `"expander": "8gt"` for the gate model or `"expander": "8cv"` for the CV
model. Existing profiles without `expander` retain their original 8CV behavior.

The **ESX-8GT is eight 0/5 V gate outputs**, not a pitch CV converter. Its byte is
a bitmask updated every audio sample: jack 1 is `0x01`, jack 2 is `0x02`, through
jack 8 at `0x80`; `0x00` turns all gates off and `0xff` turns all on. Input
hysteresis matches the manufacturer's encoder: set at 1 V or above, clear below
0.5 V, hold between those thresholds. Profiles accept `gate1`–`gate4`, `clock`,
`reset` and `run` for this expander. Send pitch, velocity and continuous automation
to a CV-capable output such as the ES-3; those signals are rejected on an 8GT.

The implementation matches the manufacturer's [8GT, 8CV and ES-40 Rack encoders](https://github.com/expertsleepersltd/vcvrack-encoders/tree/95496e8a955407889bbab94cf404cf356802bb76/src).
It uses signed integer PCM with the encoded 24 bits at the top of each sample,
with PortAudio clipping and dithering disabled. This avoids float-conversion
category selection in HydraPy. It **does not** prove that PipeWire, JACK, ALSA,
the interface mixer, or the physical digital link preserves those bits.

## Start with one ES-40 on the Digi 003

For the current rack, start with one ES-40 and one **ESX-8GT** on the Digi 003's
coaxial S/PDIF connection. Copy [the single-unit profile](examples/digi003-es40.json)
to `my-cv.json`. Replace its device-name placeholder. It selects `8gt` and
**header 1 provisionally**, based on the reported ribbon connection; confirm the
physical connector before output. Jacks 1–4 carry track gates, 5 clock, 6 reset,
7 run; jack 8 stays off. The sample rate is a 48 kHz example; match the interface's
current rate (44.1 or 48 kHz). Use the isolated diagnostic below before this score
mapping, which intentionally drives several gates.

The Linux `snd-digi00x` driver declares 8 analog + 8 ADAT + 2 S/PDIF channels at
44.1/48 kHz and writes the PCM channels in order. From that driver layout, the
profile uses **zero-based `[16, 17]`** for the native S/PDIF pair (outputs 17–18).
This is a source-derived starting point, not detection of this machine's
PortAudio/PipeWire routing. Confirm the selected audio device exposes that full
layout; a stereo virtual device or remapped graph can use different indices.
The `[8, 9]` pairs in the generic two-unit example below are not Digi 003 presets.

Read-only information to collect on Ubuntu:

```sh
hydrapy devices
aplay -l
pw-link -o
pw-link -i
```

`hydrapy devices` identifies PortAudio devices and channel counts; `aplay -l`
identifies ALSA hardware. The `pw-link` commands list current PipeWire ports and
may show a remapped route; they do not connect or change anything. Channel counts
alone do not prove which physical socket receives a stream.

The control direction is **Digi 003 S/PDIF OUT → ES-40 S/PDIF IN**. A return cable
from ES-40 OUT to Digi 003 IN is not required to drive the gate expander; the ES-40's
output is used by input-expansion options such as ES-7. Do not select external
S/PDIF clock on the Digi 003 merely because a return cable is present. Keep one
clock master for the existing rack; if using the Digi 003 as master, use its
internal clock and let the ES-40 lock to its output.

The reported input-lock LED is already lit. That establishes digital lock, not
correct gate data. The reported failure was **VCV's 8GT Encoder driving all eight
gates when only input 1 was high**. The 8GT Encoder was the correct model. This
does not establish that PipeWire, a bit-depth conversion, or a channel map caused
the failure; use the isolated diagnostic below to narrow it down.

Sources: Linux [channel counts](https://github.com/torvalds/linux/blob/master/sound/firewire/digi00x/digi00x-stream.c)
and [PCM writer](https://github.com/torvalds/linux/blob/master/sound/firewire/digi00x/amdtp-dot.c),
and the [ES-40 connections/lock indicator](https://www.expert-sleepers.co.uk/es40usermanual.html).

## Add the second unit later

Install `hydrapy[cv]` and use `hydrapy devices` to identify the audio devices and
output channel counts. Save a JSON profile like the following, replacing both
device names, the **zero-based** S/PDIF channel pairs, and the physical ES-40
header numbers. These channel numbers are examples, not detected Digi003 or
Scarlett assignments. Expander jack numbers and ES-40 headers are **one-based**.
The example below illustrates CV expanders, not the current rack's gate model;
set `expander` and the signal map to match each attached expander.

```json
{
  "format": "hydrapy-cv-1",
  "devices": [
    {
      "device": "REPLACE with first interface name",
      "samplerate": 48000,
      "es40": [{
        "name": "ES-40 A",
        "channels": [8, 9],
        "header": 1,
        "expander": "8cv",
        "map": {"1": "pitch1", "2": "gate1", "3": "pitch2", "4": "gate2",
                "5": "clock", "6": "reset", "7": "vel1", "8": "z"}
      }]
    },
    {
      "device": "REPLACE with second interface name",
      "samplerate": 48000,
      "es40": [{
        "name": "ES-40 B",
        "channels": [8, 9],
        "header": 1,
        "expander": "8cv",
        "map": {"1": "pitch3", "2": "gate3", "3": "pitch4", "4": "gate4",
                "5": "run", "6": "reset", "7": "roll", "8": "feedback"}
      }]
    }
  ]
}
```

```sh
hydrapy studio patches/gorgon_corridor.py --tracker --cv-profile my-cv.json
```

Use the actual patch path for your workspace. If both S/PDIF pairs are on one
interface, put both units in that device's `es40` list with distinct channel
pairs; HydraPy opens one audio stream per device. Optional `"direct": "0=clock,1=reset"`
on a device adds direct DC outputs on other channels in that same stream. Profiles
reject overlapping routes. Two devices share the musical playhead, but independent
hardware clocks and output latencies still require workstation measurement. Set
`--cv-offset-ms` after measuring; a common offset does not correct different
per-device latencies. Use 44.1 or 48 kHz, matching the audio device and digital
clock. High-rate SMUX is not implemented.

## CV expanders and pitched voices

An ESX-8CV receives eight 12-bit CVs in factory-calibrated mode (384 DAC counts
per volt, roughly ±5.33 V). All eight outputs update once per 24 audio samples:
2 kHz at 48 kHz. Updates are staggered, so pitch and gate are not physically
simultaneous. Studio latches all eight CVs at each cycle boundary so a note change
cannot open a later-numbered gate with the previous cycle's pitch. Put pitch
before its gate in the jack map; measure the receiving voice's response before
relying on very short triggers. This voltage protocol is incompatible with 8GT.

Unused expander jacks are explicitly sent zero volts. Pitch uses the same notes
and key transposition as the browser's FM/Sub voices, default C4 = 0 V and 1 V/oct.
`--cv-pitch-zero` changes the MIDI note at 0 V. Outputs clip at the expander's
12-bit range. Use the factory-calibrated range: the expanded-range jumper changes
the voltage scale and is not handled by this encoder.

## Establish the digital path before using a score

1. Check the ES-40's input-lock LED. No lock points to the S/PDIF route, cable or
   clock before note generation. Use its S/PDIF input; its output is for ES-7
   expansion, not a pass-through connection for a second ES-40.
2. Confirm which of the five ES-40 expansion headers holds each expander. If
   changing ribbon connections, power the rack down first; follow the manufacturer's
   orientation instructions. Configure that header in the profile/VCV encoder.
3. Generate an independent 18-second **gate** diagnostic for the current ESX-8GT:

   ```sh
   hydrapy es40-check --expander 8gt --header 1 --samplerate 48000 -o es40-gates.wav
   ```

   Route this **data WAV only to the ES-40's S/PDIF pair**, at unity, with no
   fades, pan law, normalization, effects, sample-rate conversion, dither, or other
   audio mixed into that pair. It is not listening audio. Match the file and device
   rates. All eight gates should be off for one second, then jack 1 alone high
   (5 V) for one second, all off for one second, jack 2 alone high, and so on
   through jack 8, ending with all off. The CLI requires `--expander` explicitly
   to avoid silently generating the wrong protocol. Only for an actual ESX-8CV,
   use `--expander 8cv`: that diagnostic sends 1 V to each jack in turn.
   A recording of the digital path can be compared against the original PCM
   to locate bit changes; it must itself preserve PCM bits.
4. Once that works, launch Studio and test one track gate. Test the second
   unit separately when it is connected, then test both together. Verify pitch
   intervals separately on the CV-capable outputs. Normal shutdown
   clears outputs, but a crash or unplugged cable may leave the expander holding
   its last voltage; do not treat loss of digital audio as a zero-CV command.

For this gate expander in VCV, the documented chain is **gate sources → 8GT Encoder → matching input
1–5 of ES-4(0) Encoder → Audio module's S/PDIF L/R pair**. The ES-4(0) Encoder
also has Category A/B/C in its context menu, affecting float-to-PCM scaling.
Confirm the interface's required category and keep the complete digital path
bit-preserving. These are troubleshooting checks, not a diagnosis of why either
unit failed on this workstation. The diagnostic WAV bypasses VCV's encoder and
helps separate patch configuration from the downstream digital path.

### A concrete check for the all-eight-gates symptom

For header 1, gate 1 alone is signed 24-bit PCM **left = +65536, right = 0**.
Negating the left sample changes the header byte from `0x01` to `0xff`: all eight
gates. An automated test reproduces this transformation. A polarity inversion
somewhere in the signal path is therefore one candidate to check, **not a
diagnosis of this machine**. Do not add an inversion as a fix without measuring
the path. Gain, mixing, resampling and VCV's PCM category can also change data.
Simple 24-to-16-bit truncation preserves header 1's upper byte for this test
pattern, so reduced bit depth alone is not sufficient to explain this particular
symptom. Other headers, particularly header 5, depend on lower bits.

Manufacturer references: [ES-40 manual](https://www.expert-sleepers.co.uk/es40usermanual.html),
[ESX-8GT](https://www.expert-sleepers.co.uk/esx8gt.html),
[ESX-8CV manual](https://www.expert-sleepers.co.uk/esx8cvusermanual.html),
[VCV encoder connections](https://www.expert-sleepers.co.uk/vcvrack_encoders.html).

## Polarity control in the tracker

Start Studio with `--cv-profile`, then open **Output routing** in the Gorgon GUI.
Each active ES-40 pair has a polarity selector: **Normal**, **Invert left**,
**Invert right**, or **Invert both**. For the header-1/gate-1 symptom, try
**Invert left** on the pair feeding that ES-40, then repeat the isolated test.
The change takes effect on the next output callback and is saved in the
workspace's `.hydrapy/outputs.json`. Returning to Normal removes the correction.
The profile can also supply an initial `"polarity": "invert_left"` in its ES-40
entry; a saved GUI setting for the same device/channel pair takes precedence.

The correction negates the **encoded PCM**, after packing. It does not invert
ordinary direct CV or listening audio. This can compensate a polarity reversal;
it cannot undo gain, mixing, channel swaps, resampling or lost bits. A signed
24-bit sample of −8388608 has no positive counterpart: negation saturates at
+8388607, increments a clipping counter, and displays a warning. Header 1 with
only gate 8 high reaches this endpoint. Thus even two polarity reversals are
not guaranteed to preserve every gate combination; check a digital capture
through the actual path before treating compensation as verified.

The same control works with native JACK/PipeWire CV: use `--cv-backend jack`
or `"backend": "jack"` in the profile's device entry. The `device` string then
names the JACK client, and pair indices select its named output ports. Patch
those ports directly to the hardware S/PDIF pair; see the
[native CV routing example](gorgon-audio.md#es-40-data-stays-on-its-own-route).

## Reproduce the software checks

```sh
python -m pytest -q tests/test_es40.py tests/test_output_settings.py tests/test_tracker_cv.py tests/test_studio_tracker.py
HYDRAPY_BROWSER_TESTS=1 python -m pytest -q tests/test_studio_tracker_browser.py
PYTHONPATH=. python tools/benchmark_tracker_cv.py
```

Protocol tests compare both encoders on all five headers against fixtures generated
by the pinned manufacturer C++ source. They cover all 256 gate masks, threshold
hysteresis across blocks, gate isolation, mixed gate/CV units, pause/mute/error
clearing and shutdown, as well as voltage words, clipping and packet boundaries.
Every sample of the gate diagnostic is checked, including zero intervals and
other headers; fake-device tests check configuration, integer output and cleanup.
The fixture generator is in
`tests/fixtures/make_es40_reference.py` and requires a compiler and an upstream
checkout at the pinned commit.

A container run with Python 3.13.16 and 2,000 measured 256-frame blocks gave
0.63 ms median / 0.83 ms p95 / 0.97 ms p99, versus 5.33 ms per block at 48 kHz,
for dense four-voice patterns, full automation and two **8CV** units, while the
regression suite was also running. This measures
callback computation without audio hardware, not a real-time scheduling guarantee.
The physical Ubuntu interfaces, S/PDIF bits, expanders, tuning, inter-device drift
and A/V latency remain unvalidated.
